FAILURE TRIAGE CASEBOOK

Each case is one attempt by a coding agent to fix a GitHub issue. The attempt failed: the agent's patch is known to fail at least one of the FAIL_TO_PASS tests, which come from the upstream fix and were hidden from the agent. The agent's log shows only the tests the agent chose to run itself. When the log says its tests passed, that does not mean the upstream tests pass, and it is not evidence that the upstream tests are wrong.

For each case a reviewer reads the issue, the FAIL_TO_PASS test names, the gold patch (the upstream fix), the agent's patch and a condensed log of what the agent ran. The reviewer then records why the attempt failed, as one JSON object on one line.

Failure classes, in precedence order. When more than one fits, the first one wins.
1. env_broken: the environment stopped the agent before code quality mattered: a missing dependency, a broken install, the package does not import, or a network error or timeout in the sandbox.
2. task_underspecified: a careful engineer could not infer from the issue what the upstream tests check, such as exact names, messages or formats that the issue never mentions.
3. upstream_tests_wrong: the tests check something other than the issue, or reject a reasonable fix.
4. model_failure: the task was fair and the agent's patch is wrong, incomplete, or missing because it ran out of turns.
5. unclear: not enough evidence to decide.

Most failed attempts are model_failure. The reviewer picks another class only when the case shows specific evidence for it.

The reviewer checks in this order:
a. Did errors in the log stop the agent from running the code at all? Then env_broken.
b. Where does the agent's patch behave differently from the gold patch? That difference is what the FAIL_TO_PASS tests catch.
c. Does the issue state the behavior the gold patch has there? If it does, or a careful engineer reading the issue and the code would get it right, the agent missed it: model_failure. If the issue never states it and the agent's choice is another reasonable reading, task_underspecified.
d. upstream_tests_wrong is rare. It needs a test that checks behavior the issue does not ask for at all, or that rejects a patch doing exactly what the issue asks. A gold patch that looks close to the agent's patch is not such evidence: the difference from step b is still there.

The verdict has three keys. "evidence" names the difference from step b, quotes the lines of the issue or the patches that decide the class and, unless the environment was broken, ends with "The issue states it." or "The issue does not state it." "failure_class" is one of the five classes. "confidence" is a number from 0 to 1.
